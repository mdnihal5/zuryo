# Correctness review (2026-10-19, payments added the same day)

Goal: try to break every path that changes state or money. Every scenario below is an automated test in `api/test/adversarial*.test.ts` (or an older test file where noted) and passes on Postgres 16 and, apart from the note under "Postgres 18.6", on 18. Tests run against a real throwaway Postgres through the real HTTP stack.

## Bugs found and fixed

| Bug                                                             | Root cause                                                                                                                                                                       | Fix                                                                                                                                         | Regression test                                                             |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Booking lock could leak and block a trainer forever             | `insertBooking` used a session-level `pg_advisory_lock` released in `finally`; if the transaction was already aborted, the unlock failed and the pooled connection kept the lock | Transaction-level lock (`pg_advisory_xact_lock`) per zone, released by Postgres at commit or rollback                                       | "a transaction that fails after taking the zone lock leaves nothing locked" |
| Falling through trainers could deadlock                         | Holding one lock per tried trainer until commit lets two requests wait on each other (seen as `40P01`, 16 and 20 errors in the herd)                                             | One lock per zone, taken once, so no request ever holds two                                                                                 | stress herd, zero 5xx                                                       |
| Time off and a booking could both be accepted for the same hour | Booking checked eligibility, time off checked bookings, with nothing between them                                                                                                | Both take the zone lock before checking                                                                                                     | "time off and a booking racing for the same hour never both succeed"        |
| A session could run past midnight                               | Working-hours check compared times of day, so 23:30 + 60 min = 00:30 passed `end_time >= 00:30`                                                                                  | Session start and end must fall on the same Kolkata date (a session ending exactly at 24:00 is not offered; `end_time` cannot represent it) | "a session may not run past midnight"                                       |
| Huge ids gave 500                                               | `idSchema` accepted numbers above the Postgres int range                                                                                                                         | `.max(2147483647)`                                                                                                                          | "huge, negative and odd ids"                                                |
| NUL character in text gave 500                                  | Postgres text cannot store `\u0000`; zod allowed it                                                                                                                              | `plainText()` helper for comment, time-off reason, notes, exercise names, profile tags                                                      | same test                                                                   |
| Hours edit could leave a trainer with no hours or return 500    | Delete then insert ran on separate pool connections, not in one transaction                                                                                                      | One transaction, trainer row locked first                                                                                                   | "two parallel edits of the weekly hours"                                    |
| Cancel racing session start answered 200 with a running session | Conditional UPDATE lost, but the service returned the fresh row anyway                                                                                                           | If the booking is not cancelled afterwards, `409 BOOKING_NOT_CANCELLABLE`; start answers `409 SESSION_NOT_STARTABLE` when it lost           | "cancel racing session start"                                               |
| `scripts/stress.ts` seed was out of date                        | The trainers table gained NOT NULL columns                                                                                                                                       | Seed supplies them                                                                                                                          | `npm run stress` runs                                                       |

## Scenarios that passed without a change

Idempotency: same key and body replays; same key with a different body is 422; same key from two customers is two bookings; a key whose first attempt failed (no trainer) works later; 5 parallel requests with one key (create and reschedule) give one booking, one charge; replay after the original committed.
Atomicity (fault injected with a trigger that fails the notification insert after the booking, payment and ledger rows are written): create, cancel and reschedule leave no partial rows, and the same key works afterwards.
Double writes: two parallel cancels (existing test); two reschedules with different keys give one 201 and one 409; cancel racing reschedule keeps money equal to active bookings; the last package credit from two tabs gives one success, `PACKAGE_EMPTY` for the other, balance 0; rescheduling a booking paid with the last credit keeps the balance at 0; a reschedule clashing with another of my sessions leaves the old booking confirmed; sweep and read completing one session (existing test); two package purchases with one key (existing test).
Time edges (clock faked with `vi.setSystemTime`): cancel at exactly 2 h is refunded, 1 ms later is not; peak 08:30 yes, 09:00 no, 20:30 yes, 21:00 no; instant booking at 19:45:00 sharp is accepted, 1 ms later (session would end after 21:00) is refused.
Auth: expired, wrong-secret, `alg: none` and old-version tokens are 401; `role`, `customerId` and `totalPaise` in bodies are ignored; another trainer's session (start, read, record read and write) and time off are 404; notifications are private; customers get 403 on admin routes (existing tests cover the rest of the IDOR matrix).
Validation: oversized body 413; wrong types, comment over 2000, `limit=0`, bad cursor, 31 February, array for a date, negative ids, short idempotency key are 400; unknown fields are ignored.
Pricing: an admin rule change racing six bookings leaves every booking with a consistent snapshot.

## Payment gateway flow (MockPay, webhook)

Automated in `api/test/payments.test.ts`, `adversarial-money.test.ts`, and the stress invariants. Real Postgres, real HTTP.

| Scenario                                                                                              | Result                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Webhook with a missing, forged, non-hex or wrong-secret signature, or a body signed for another order | 401, order and booking unchanged                                                                                                                          |
| Validly signed body with a different payment amount or order amount                                   | 422 `PAYMENT_MISMATCH`, nothing changes                                                                                                                   |
| Unknown order id, malformed body                                                                      | 200 `ignored` / 400                                                                                                                                       |
| Same success webhook sent 5 times at once                                                             | one `confirmed`, four `replay`, one paid order, two notifications                                                                                         |
| Failure webhook, then repeated                                                                        | booking `payment_failed`, slot immediately bookable by another customer, repeat is a no-op                                                                |
| Pending hold, another customer books the same trainer and time                                        | 409 `NO_TRAINER_AVAILABLE`                                                                                                                                |
| Hold past its time, no sweep running                                                                  | next read or booking releases it (`expired`), the slot sells to someone else                                                                              |
| Success after expiry, slot free                                                                       | booking confirmed, order `paid`                                                                                                                           |
| Success after expiry, slot taken                                                                      | order `refunded`, booking stays `expired`, customer notified, replay is a no-op                                                                           |
| Same Idempotency-Key retried (also 4 in parallel)                                                     | same booking, same order, one order row                                                                                                                   |
| Cancel of a paid booking, 3 parallel                                                                  | order `refunded` once, one set of cancel notifications                                                                                                    |
| Package bought online                                                                                 | not usable (404 as `packageId`, absent from list) until the paid webhook; failed payment never activates it; retry with the same key shows the same order |
| Webhook transaction fails midway (notification insert fault-injected)                                 | 500, order still `created`, booking still `pending_payment`; the gateway's retry then succeeds                                                            |
| MockPay completion on the hosted page                                                                 | the booking is still `pending_payment` until the signed webhook is delivered; completing twice sends one webhook                                          |
| Trainer visibility                                                                                    | unpaid, failed and expired bookings are not in the trainer's list and are 404 by id; nobody is notified before payment confirms                           |

Stress (`npm run stress`, 60 s): herd winners and 50 retry-storm customers pay through MockPay's real HTTP webhook; mixed load pays 70%, fails 15% and abandons 15% of its bookings. Added invariants: every pay-now booking has exactly one order whose status matches the booking (confirmed means one paid order, pending means `created`, failed means `failed`), no paid order behind an unconfirmed booking, no payment id on two orders, no trainer notified about an unpaid booking.

## Postgres pooler (Supabase)

The zone lock is transaction-level, so it works through Supabase's transaction-mode pooler (port 6543): the pooler keeps one server connection for the whole transaction, and Postgres drops the lock at commit. The old session-level lock would not have been safe there: lock and unlock can run on different server connections, leaving the lock held by a connection some other client gets. `pg` uses no named prepared statements here, so transaction mode needs no other setting.

## Postgres 18.6

On the local Postgres 18.6 build, concurrent runs occasionally ended with two active bookings for one trainer at the same time (in `concurrency.test.ts` and once in `npm run stress`), including with the original code and including with the zone lock. On Postgres 16.15 the same tests and stress pass every time. I could not reproduce it with sequential inserts or a reduced concurrent script and did not find the cause. Treat as unresolved: check on the Postgres version production uses.

Follow-up check (same day): a raw-SQL reproduction on 18.6 (50 concurrent transactions per round, 3 trainers, overlapping ranges, savepoint retry, the same partial btree_gist exclusion constraint) found 0 overlaps in 40 rounds, and `concurrency.test.ts` passed 6 of 6 consecutive runs on 18.6 with the final code. So the constraint itself holds on 18.6; the earlier failures were not reproduced and happened while a second agent was loading the same machine. Still worth one run on Postgres 17 (what Supabase runs) before the demo.

## Not yet tested or known limits

- Trainer-start races under the stress load, and reschedule under load.
- Changing working hours does not move existing bookings (known limit, unchanged).
- A session ending exactly at midnight cannot be booked because `trainer_hours.end_time` cannot hold 24:00.
- A server crash between the commit and the response is covered only by the replay tests, not by killing the process.
- The `completeDueSessions` call before every read stays: it is one indexed statement (`bookings_running`), about 1 ms locally; scoping it to the rows read would add complexity and a second round trip for remote databases.
